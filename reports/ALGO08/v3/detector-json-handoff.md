# Repeated detector JSON in the integrated original-file route

The field candidate still repeats exact canonical serialization at the receiver-to-publication handoff. Even a favorable scenario that removes six selected-packet re-encodes and five probe-binding checks prices at **29 ms**, **35 ms**, and **288 ms CPU** on DS30-0016, DS30-0049 and DS30-0274. That is below 0.5% of each candidate process CPU clock. The prototype verifies immutable bytes once per reader and can carry a digest to later checks. It remains unbound to the live entry.

- **Original acquisition.** The released `algo08_scan.acquire` creates two different commitments. It hashes the original inventory and ordered window SHA list for authority, then hashes `["cancellation", raw_authority, receiver_recipe, probes]` for the analysis identity. The candidate's `full_short_raw.observe_acquisition` independently recomputes source authority from observed window hashes and verifies the pre-held analysis commitment. `unified_short_bootstrap` then calls `bind_native` on the same pre-held packet. The selector's entry and inner `select` repeat that probe binding. The original independent source proof stays paid.
- **Held lineage.** `eight_ms_held_fit.select` selects the emitted factors, then `continued_cfo_trial.rebinding` changes the detector recipe and analysis commitment. Even an `unfiltered` choice binds a new detector recipe. On all three audited cases the signed rows and matching byte lengths allow exact reconstruction of the archived pre-held packet. The pre-held and selected analysis and file hashes differ. Neither the raw authority nor these two different canonical messages can substitute for one another. A real history choice may change the rows as well.
- **Identified selected-packet encodes.** The held selector computes one whole-packet digest, then `empty_bootstrap.bind_native` re-encodes it through its `expected` check. The outer `eight_ms_native_receiver.prepare` repeats that check. The installed `algo08_scan.analyze` calls `immutable_json`, so the fourth encode goes to the durable file. It deliberately reopens and parses that file and validates its selected probe commitment. The solver receives that parsed document. The scanner re-encodes it for the terminal, `exact_named_raw.publish_active` re-encodes the original in-memory handoff for artifact evidence, and `unified_short_bootstrap` re-encodes it for the final comparison with a fresh on-disk hash. These are seven identified whole encodes on the complete positive path, with no assumed shortcut on a failed Graph guard. Distinct timings, clocks, and stock report, terminal, path, grid and image payloads remain separate.
- **Stock and independent trial verifier.** The installed fresh 20 ms path does a probe commitment in acquisition and a check after reparse, plus a canonical write and a complete canonical digest after solve. It does not run a held selector or the two extra candidate wraps. On either role the campaign verifier independently reopens and parses the durable file, checks raw lineage and detector, and compares its canonical value to the terminal. It reports a hash of the encoded file as well. Its timed scope also verifies standard artifacts and decoded PNGs. The prototype leaves that scope independent. An existing installed detector file can take the original saved-file validation route without any newly emitted bytes to reuse.

## Paid clocks and ceiling

The older calibration wrote and checked the exact 5,590,695-byte native packet from DS30-0008 twice. It measured **26.845–27.320 ms CPU** for the original full JSON encoder, **22.395–23.366 ms** for parsing, **1.536–1.551 ms** for readback and **26.149–26.194 ms** for source verification with its probe SHA and file digest. Fsync and full file write clocks varied more and stay paid. This receiver-to-publication report uses the larger archived CPU rate for each operation, divided by file size and multiplied by the actual current file size. The source-verification rate covers the whole recorded verification scope and therefore gives a deliberately generous allowance for one duplicate probe check. Different packet structure or caches could change the actual rate. [Disjoint archive seal calibration](full-short-seal-scaling.md)

## Exact-byte prototype

`NativePacketBytes` owns a copy of the canonical bytes and derives its tag at snapshot construction with the released encoder. It accepts a persisted readback only when those actual bytes equal that exact snapshot. The released parser then consumes the reread bytes. It can share the exact file tag across receipts in the same invocation. It retains no mutable dictionary, invokes no parser shortcut and changes no public product. The tests covered real released immutable writes, repeats, corruption or changed factors, invalid mutable buffers and semantically equivalent noncanonical bytes. The six bound production files round-tripped byte-for-byte through the prototype. An integration would need the storage owner to accept the byte snapshot without encoding a second time, preserve file and directory durability, and distinguish sealed readback from the science worker's mutable decoded copy. Reusing a tag after mutating the parsed input or by trusting a file path, terminal label or mtime alone would change the validation semantics.

The smallest defensible reuse avoids one selected re-encode for only 2.6–26.7 ms of estimated CPU. Broader wiring across recipe, storage, solver and independent verification ports is unwarranted at this scale. No receiver, solver, rendering or live timed worker started.

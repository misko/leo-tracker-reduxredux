# The signed receiver already consumes decoded windows without a Python payload copy

Lending bounded readonly views through the actual paired SHA-256 and mixed 20/12 ms receiver reproduced every factor. It saved **0.587 and 0.093 ms of complete acquisition CPU** in the two reversed orders on one resident public member. The decoder read clock increased by **0.864 and 1.449 ms**. The pinned released C extension already decodes into the final owned Python bytes, and the digest, NumPy array and native lane calls use that same payload address. ## Copy and ownership census

The released `decompressionreader_read` allocates through `PyBytes_FromStringAndSize(NULL, size)`, passes that object's backing buffer to `decompress_input`, and returns the same object on complete reads. The resize branch handles a short read. The installed extension SHA-256 is `7eb41c8b36cd99ed6c67e39f8574e42472687a14c6038c512bb3a90b7082616d`. The binding comparison therefore addresses allocation and buffer ownership at the Python boundary. Zstandard's internal history and buffer handling remain outside this source observation. The native detector still performs its required CI16-to-working-format operations. [Disassembly and observation pins](measurements/scoped-window.json.gz)

Introducing an extra owned `bytes` copy of the **102,400,000 decoded bytes** consumed **6.195 ms median CPU** across eight alternating-order controls. The readonly-view operation itself used about **0.010 ms** across the 64 windows. The price of one such added copy would be **0.657 CPU s** at 106 equivalent dense members, conditional on transferring this single-core memory rate. The released boundary already avoids it. The earlier bounded native ring does copy out of Zstandard history. The member advertises **524,288 bytes** of history and rounds to a **786,496-byte** ring, smaller than one **1,600,000-byte** stereo window. A whole-window loan cannot use that ring unchanged.

# Staged PNG writeback on the saved DS30-0057 publication

Writing all eight PNGs before syncing them preserved every byte of the archived DS30-0057 publication. It reduced elapsed time by **16.763 ms** when it ran second and added **1.435 ms** when it ran first. This pair of orders establishes the change in write scheduling. The direction of the timing effect reversed with order, leaving a repeatable speedup unestablished. [Timing and fsync receipt](measurements/png-writeback-DS30-0057.json)

| Order | Build | Publish elapsed | Publish CPU | PNG fsync wait |
|---|---|---:|---:|---:|
| Installed → batched | Installed | 35.342 ms | 6.666 ms | 20.830 ms |
| Installed → batched | Batched | 18.580 ms | 5.945 ms | 9.223 ms |
| Batched → installed | Batched | 19.667 ms | 5.889 ms | 10.248 ms |
| Batched → installed | Installed | 18.232 ms | 5.598 ms | 9.137 ms |

The installed implementation syncs each distinct PNG immediately after its write and flush. The prototype writes and flushes every distinct PNG inside the private compact staging directory, then calls `fsync` once on each open descriptor. At the first PNG sync, the installed stage contained one PNG and 1,805,521 bytes, and the prototype stage contained all eight PNGs and 8,166,750 bytes. Both made **14 synchronous calls** before the inherited atomic directory rename. Eight calls covered distinct PNG inodes, three covered the immutable grid, path and manifest files, and three covered their staging directory. Batching lets writes reach the filesystem before the first blocking PNG sync. The eight sync calls still complete serially. [Research variant](batched_png_writeback.py) · [Sync order and inode checks](measurements/png-writeback-DS30-0057.json)

All four runs reproduced the same eight content-addressed PNG names, bytes, grid, path and manifest. A duplicate figure shared its content address and was synced once. Tests injected a `KeyboardInterrupt`, a sync error, an invalid final PNG and a digest collision. Readers saw a pending publication during staging, descriptors closed on failure, and the unwound stage was removed. A retry then published successfully. Abrupt process death can leave a private staging directory, as with the installed transaction. The final directory becomes visible only at the rename. This study covers atomic reader visibility and handled interruption cleanup. [Component tests](../../../tests/pipeline_eval/test_batched_png_writeback.py)

The output device was `/var/tmp` on ext4, logical device `252:0` backed by `nvme0n1p3`. The earlier DS30-0057 publication timed out on `/srv/bulk`, a separate XFS volume at `252:5` backed by RAID and an NVMe cache. Three local NVMe samples immediately before the study showed at most 0.30% utilization and 0.77 ms average write wait, although host-wide I/O pressure remained high. All 2,008 pages of the 11 archived inputs were already resident when checked. Both arms used the same in-memory figures and sidecars, CPU 2, nice 15, best-effort I/O priority 7 and one uninterrupted Gauss lock. The stopwatch covers the instrumented `publish()` call only. Reading the input and checking the output hashes sit outside it. The elapsed observations apply to local ext4. The [trial driver](png_writeback_trial.py) verifies the installed publisher source and archive digests. Run it as the Gauss `leo` account with a fresh result path writable by that account, the release Python and the research checkout’s `src` and root on `PYTHONPATH`. The driver uses the shared Gauss lock, picks local ext4 when its device counters pass the health check and otherwise uses tmpfs, and removes its temporary publications after validating their hashes. An initial cache observation from the developer account stopped before any publication. Eighteen focused tests passed. The prototype lives in the research directory.

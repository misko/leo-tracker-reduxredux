# Can writer-owned detection remove the first-use replay?

**The matched complete-verification path already detects each admitted lane once and decodes the emitted capture once.** Moving that detector call onto writer-owned CI16 cannot eliminate native replay on one core. Independent post-write verification would still require every encoded block, decoded window and rolling member digest. There is no new physical run. ## Which baseline pays both requirements

The early selective trials authenticate the encoded archive and realize only the detector's demanded apertures. Some trials separately measure complete recovery. Adding that recovery to selective detection can pay more than one decode for the blocks already demanded. The later 20/8 first-use comparison closes that boundary in one traversal. Its full-readback branch reads and authenticates both parts of every window, verifies the signed window digest, updates the ordered member hash and passes the same contiguous immutable array to the real scanner. The 8 ms primary and ordinary two-scan full anchors run under the existing policy, including both antennas and the original invalid-window exclusions. Scanner completion exhausts the iterator and checks the full decoded digest. Only then can the recorded native packet, EOF decision and output become authoritative. ## What moving DSP can remove

With the same writer, complete verification and detector, the exact eliminated workload is **zero detector passes, zero packed frame decodes and zero encoded or decoded digest checks**. On a single core, reordering the same work does not create a CPU saving. If all existing verification code still runs, early detection would merely move the detector and require binding provisional output after the durable root is known. It may also spend DSP on data later rejected. The staged incremental ingress experiment already demonstrated private provisional DSP followed by safe refusal on a late corrupt checksum. Its input was arriving compressed data, distinct from writer-owned samples. Early first-window availability and time spent waiting for RF could have different elapsed-time implications. Neither is part of this resident single-core CPU comparison. [Previous provisional calculation and late refusal](incremental-ingress.md)

A verifier specialized for checksum-only readback could avoid concatenating the two decoded parts for a consumer that no longer takes the returned samples. That is a separate verifier change. The byte ceiling from the measured one-pass source is one concatenation per verified window, at most **102,400,000 output bytes** on the physical member, plus the cheap array views. The earlier disjoint DS30-0008 profile measured **5.326–5.698 ms CPU** to concatenate equal-size prefix and tail views of the authenticated owned samples. Eliminating a join costing that much would save about **1.3–1.4%** of its prior complete first-use CPU, before any provisional-state handoff or changed memory locality. That price is measured on owned views and is not an upper bound for every allocator or physical storage layout. Prefix-state reuse already shows how to preserve the full-window hash without depending on a contiguous joined buffer. Eliminating the join would still require every original part decode and hash, and the aggregate would have to consume the parts in their original order. [Measured SHA and join costs](ci16-sha-reuse.md)

The zero-replay ceiling is structural. The only distinct savings opportunity identified here is the verified output copy, for which the existing physical evidence does not justify a new writer-side detection path.

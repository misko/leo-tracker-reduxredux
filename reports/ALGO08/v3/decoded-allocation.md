# First-touch cost on a signed physical receive member

The normal allocator already reused the heap on all 64 decoded windows. A private 2 MiB `M_MMAP_THRESHOLD` saved **6.631 and 0.511 ms** of authenticated acquisition CPU in the two reversed pairs. Only **1.061 and 0.545 ms** came from the observed decoder reads, which incurred three fewer minor faults per traversal. The larger difference in the first pair included **4.128 ms** in the unchanged signed native detector. Both comparisons fell short of the frozen 25 ms acquisition screen. Peak RSS was effectively unchanged. The study stopped after the first staged member. ## Why the South clocks prompted this check

The recent same-build South containing and omitted runs had the same signed detector packet, probes and owners. The source was fully resident. Process minor faults rose from **114,169 to 584,938**, system CPU from **0.560 to 4.891 s**, and user CPU from **10.121 to 10.372 s**. Authenticated acquisition contributed **3.564 of the 4.582 s CPU gap** (5.135 to 8.699 s). Decision and publication contributed another **1.045 s** (4.966 to 6.010 s). The omitted process recorded 40 input blocks, two major faults and 2,209 involuntary switches. The containing process recorded zero input blocks, zero major faults and 752 involuntary switches. Stage clocks have no split system or fault counters. The extra minor faults are on the scale of the 1.92 GB decoded stream if each represented a 4 KiB first touch. They also permit faults from allocator, mapping and file-backed setup elsewhere in either process. [Containing archive](measurements/combined-raw-south.json.gz) · [Original omitted receipt](/dev/shm/leo-v3-south-omitted-raw01/result.json)

Earlier work already tested a shared 102.4 MB Zstandard destination, a bounded 8 MiB output ring, and the original owned-window backend through a borrowed view. The ring traded lower RSS for single-core timing differences that changed sign across the pair. In the owner-retaining view study, the original decoder's `read(size)` already delivered the final owned span without an extra NumPy copy. A separate compressed `readv` pool removed 344 first-touch faults per read in its fixture, with a **3.92 ms** median acquisition saving and substantial per-arm variation. The current test retains all original owned bytes and directly observes whether the process allocator actually faults them repeatedly. ## Matched physical test

The first signed DS30-0016 member has **78,554,951 compressed bytes** and **97.656 MiB of decoded IQ**. The index and member were already staged on tmpfs and all **19,222 input pages** were resident before and after each child. Each fresh process ran the same verified 20/12 ms guarded and selective receiver using the release's signed member reader and Zstandard C backend. The single experimental intervention was a glibc 2.43 allocation threshold set after runtime imports. All runs had zero input blocks and zero major faults. The child launch included through-exit time. The narrower acquisition clock includes source verification and receiver work. The original read returned independently owned bytes on all four runs. The decoder recycled **five payload addresses** over the 64 windows in each child. Output addresses fell inside the heap every time. First-window decode incurred 585 minor faults and 1.985–2.013 ms CPU. The next seven reads incurred 771–772 faults. The remaining 56 reads incurred 390–392 combined faults, about seven per window. At 4 KiB per page, touching a fresh 1.6 MB destination each time would be roughly 391 faults per window. Full decode read counts were **17.910 faults/MiB by default** and **17.879 faults/MiB with the threshold**. The observed system CPU in these decode scopes ranged **0.012–0.020 ms/MiB** by default and **0.011–0.022 ms/MiB** with the threshold. The first versus later read grouping uses separate observers inside each fresh process.

The signed compressed member read itself incurred 273 minor faults in each child and cost **31.79–32.21 CPU ms**, including **13.94–15.00 ms** system CPU. About 177 MiB peak RSS persisted across all four exits. The threshold reduced final anonymous RSS from **75.4 to 62.2 MiB** at the post-acquisition snapshot and reduced the final glibc heap extent from **55.9 to 34.3 MiB**. The process allocator setting acts beyond Zstandard, so those process-wide differences do not locate the savings in its window output. Peak and final RSS describe different times. Every child matched the previous guarded native packet at `ce5af5611b56a42ba960e6d1296040b2bbf4ad8e60aea96d182e9ff6f94e3111`. The 64 IQ hashes and native traces matched, including 58 admitted stereo opportunities, 16 full and 100 short calls, all original and refined probes, seven attempted CFO corrections, six edits and the held route's 45 selected factors. Acquisition ended at a verified detection seal. There was no positioning or full-recording timing. The full South system CPU discrepancy remains unassigned. In particular these four physical launches reproduced neither its sustained fault rate nor its system CPU gap. [Parity gate and scorer](decoded_allocation_score.py)

Use freeze `263d6bf63` and the installed release Python with the source roots in the [bound launcher](decoded_allocation_trial.py). Run `decoded_allocation_trial.py run FRESH_TMPFS_OUTPUT` with the Gauss shared lock, CPU 2, nice 15, I/O priority 7 and one numerical thread as `leo`.

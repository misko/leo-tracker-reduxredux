# Measured Ku-band field cohort

StarLoc released 11 captures made with the same three-channel receiver array at several physical locations in one geographic area. Each recording is 900 seconds at a nominal RF center of 11.325 GHz. This cohort tests transfer to a separate hardware installation with field tracks from multiple stationary locations in that area. It supports a receiver-side location check conditional on prepared beacon-frequency tracks. The captures offer one past constellation and one RF channel, with points accepted by the source when the three synchronized receiver channels detected a common FFT bin. The packet represents that common observation as receiver 1 and uses the source's one-based Ku channel 3. [Paper and experiment setup](https://arxiv.org/html/2604.21147v1#S5.SS1), [data release and capture specification](https://zenodo.org/records/19043854).

The processed inputs were `data/<capture>/tracked_tones.mat` and `data/<capture>/Starlink.tle`, the per-capture `data/imus/imu_utctime_*.txt` logs, and the capture-start timestamps in `utils/helper.py`. The first capture's same-time GNSS log is present in the release even though the reproduction helper points its first two entries at the second capture's log. The cohort uses the first capture's own log. Measurement times are offsets from the original SDR start timestamps stored to nanoseconds in the public observation envelope. The GNSS location uses the median WGS84 latitude and longitude from eight 64 KB byte-range samples spread across each IMU log. Temporal coverage, GNSS spread around the median, height summaries, and input digests are in `source_provenance.json`. GNSS logs establish stationary receiver truth, with their sample spread reporting stability rather than surveyed absolute accuracy. A conservative 500 m threshold gives eight groups, matching the authors' report of eight physical locations. Captures in the same group still use their individual GNSS positions as ground truth. [Pinned processed release](https://github.com/GiddaZhang/Starloc/tree/fc010f950dfac5ac6d7a345db24513217fbb81d5), [capture timestamp and reproduction helper](https://github.com/GiddaZhang/Starloc/blob/fc010f950dfac5ac6d7a345db24513217fbb81d5/utils/helper.py).

The input frequencies are the first two columns of the released `main_tone_dict` arrays. The author pipeline joins measured FFT points by time, frequency, and beacon harmonic spacing inside predeclared time windows. In the published preprocessing code, the measured track exists before the optional location-dependent satellite matching. That later stage calculates categorical IDs and offsets for a plot, and saves the IDs separately. The benchmark exports neither field. The construction of the predeclared windows is undocumented. The released arrays also retain five columns and repeated timestamps, while the current preprocessing source consolidates those rows before export. This package preserves the measured baseband Hz as published and does not assert that the current preprocessing revision exactly regenerates every distributed array. The per-time median combines repeated frequency observations, and the central recorded timestamp in each 0.5-second bin controls density. A measured overlap and near-integer tone separation identify likely duplicate passes. The longer track is kept when both measured tracks agree over the overlap under the stated fixed thresholds. No satellite ID, site match, fitted Doppler curve, or receiver prediction is used to filter or adjust the measured frequencies. [Window and extraction implementation](https://github.com/ConnectedSystemsLab/starloc_preproc/blob/main/starlocProcessRawSignal/obs_periods.json), [frequency track construction and later ID stage](https://github.com/ConnectedSystemsLab/starloc_preproc/blob/main/starlocProcessRawSignal/utils/track_centertones.py#L124-L321), [source array contract](https://github.com/GiddaZhang/Starloc/blob/fc010f950dfac5ac6d7a345db24513217fbb81d5/data/README.md).

The source states that it fetched the CelesTrak supplemental Starlink catalogue at the start of each capture. The processed artifact supplies matching orbit files, and an independent retrieval receipt with an exact acquisition timestamp is unavailable. The public observation therefore uses the capture start as the documented availability bound and cutoff. Several supplemental source forecasts contain future-dated orbital element epochs. For each query, the package combines the catalogue supplied for that capture with earlier source releases already available by the same cutoff, selecting the latest element per NORAD object with an epoch at or before the cutoff. The package never uses a later source release to fill an earlier capture. [Catalogue acquisition and filename specification](https://zenodo.org/records/19043854/files/starloc_full_dataset_README.md?download=1).

Every capture appears in a matched present/missing query pair with the same observations and catalogue. Both offers are randomly rotated rectangular grids of four 25 km squares and share two decoy squares along one edge. The missing offer reflects the grid across that shared edge. The present square center is jittered up to 9 km per axis from the actual receiver. Alternating chronological captures have 37–60 km or 60–150 km grid edge lengths. The 37 km lower bound clears the diagonal of a 25 km square at arbitrary orientation. All query and region IDs are opaque, and the independent geometry choices were generated before any receiver result.

The local search inspected `corpus/manifest.json`, `corpus/recording-ingest-v1.json`, station deployment manifests, and the field inventory from `/mnt/qnap01/mouse9911/satellites/leo-tracker`, `/mnt/qnap01/mouse9911/leo`, and the local/QNAP orbit archives. The DS26 and DS29 location references describe the same installation, and the older named field tree exposed only one explicit station directory in the inspected inventory. The local orbit archives inspected cover 2026, outside the external data's capture dates. No local capture was added to this field cohort. External alternative evidence included raw passive-scan power matrices and prior-night TLEs from the Watson release, a passive-receiver database with satellite detection statistics and one 100 ms IQ snippet, and Starlink Direct-to-Cell IQ at a different downlink band. These alternatives do not contribute any observations to this package. [Watson monitoring dataset](https://zenodo.org/records/8400658), [passive receiver file list](https://github.com/lukepwilson/starlink-passive-detection), [Direct-to-Cell corpus](https://huggingface.co/datasets/Morty0311/starlink-d2c-x300-duplex-iq).
